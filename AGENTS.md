# AGENTS.md

Self-hosted observability stack for studying LangChain execution, plus a real
reference app to observe:

- **Infra**: a client emits OTLP to a single Grafana Alloy collector, which fans
  out to Tempo (traces), Prometheus (metrics), and Loki (logs); Grafana
  visualizes all three. Config lives in `config/`.
- **Apps** (`app/{mock-llm,ai-service,frontend}`, compose profile `apps`):
  chat UI → LangChain agent API (SSE streaming) → fake OpenAI-compatible LLM.
  The ai-service is the reference OTel client to copy when wiring a future real
  LangChain service.
- README.md (Korean) is the user-facing guide; keep it in sync when behavior changes.

## Commands (Makefile)

- `make up` — start stack (Alloy, Tempo, Prometheus, Loki, Grafana). Does NOT start apps (profile `apps`).
- `make ps` / `make logs` — status / follow all container logs.
- `make app-up` — build + run the 3 apps as daemons (mock-llm :8100, ai-service :8000, frontend :8080).
- `make app-logs` / `make app-down` — app logs / stop+remove apps (SQLite volumes preserved).
- `make metrics` / `make traces` — verify data landed in Prometheus / Tempo (`service.name=ai-service`).
- `make down` keeps named volumes (data preserved); `make clean` = `docker compose down -v` (wipes all data, incl. app SQLite vols `ai-service-data`, `frontend-data`).

## Hard-earned gotchas (do not "fix" these)

- **Docker Compose v5.5.1 has no `--profile` flag.** Use `COMPOSE_PROFILES=apps <cmd>` env instead (see Makefile). `docker compose --profile ...` fails with `unknown flag: --profile`.
- **Alloy v1.19 CLI**: config file is a *positional* arg to `alloy run` — `--config.file` does not exist. `otelcol.pipeline` was also removed; components are wired with per-component `output` blocks as in `config/alloy/config.alloy`.
- **Reload Alloy without restart**: `curl -X POST http://localhost:12345/-/reload` (returns 200).
- **Alloy config language (River) gotchas** (verified 2026-09): comments are `//` only — a `#` line breaks the config with `illegal character U+0023`. Regexes are RE2: **no non-capturing groups** like `(?:...)` (must restructure the pattern, e.g. `^/?obs-(.+)$` instead of `^(?:/)?obs-(.+)`). `discovery.relabel` is a *target* processor and **requires a `targets` argument** (fail: `missing required attribute "targets"`); it exports `.output` and `.rules`.
- **Prometheus needs `--web.enable-remote-write-receiver`** (already in docker-compose.yml) or Alloy's remote writes are silently dropped.
- **alloy/loki/tempo images are distroless** (no shell/wget) → NO healthchecks; never add `depends_on: {condition: service_healthy}` for them. No app waits for OTLP at startup — ai-service only calls Alloy per-request.
- **Alloy spanmetrics connector**: `metrics_flush_interval` lowered to 10s; `namespace = "langchain"` → `langchain_calls_total`, `langchain_duration_milliseconds_*`. Default dimensions incl. `service_name`, `status_code` (`STATUS_CODE_ERROR` = errors), custom `gen_ai_operation_name`, `gen_ai_request_model` (set by OpenLLMetry instrumentation). **FastAPI HTTP spans also pass through this connector** → they show up as a separate `gen_ai_operation_name="unknown"` series. Dashboard panels group by that dimension, so LLM calls stay separate.
- **`opentelemetry-instrument` CLI needs `opentelemetry-distro`** (verified 2026-09). The CLI loads `opentelemetry_configurator`/`opentelemetry_distro` entry points to build SDK providers from `OTEL_*` env; `opentelemetry-distro` is what registers them. Without it the providers stay `ProxyTracerProvider` and **nothing is exported** — no error, silent no-op. Our `requirements.txt` pins `opentelemetry-distro[otlp]==0.65b0` (same series as the instrumentation core 0.65b0).
- **Logs are NOT via OTLP — they are container stdout** (verified 2026-09). Single source of truth: `docker logs <container>` content == Loki content, byte-for-byte (verified with a full diff). Alloy's `loki.source.docker` reads the Docker API (`/var/run/docker.sock`, mounted in docker-compose; the alloy container already runs as root/uid 0 so socket perms are fine). **Labels are mapped on the discovery targets, NOT on entry labels**: `loki.source.docker` strips all `__meta_*` labels from entries, so a downstream `loki.relabel` on the log stream is a silent no-op (`loki_relabel_entries_written=0`). The config instead chains `discovery.docker → discovery.relabel (rules) → loki.source.docker{targets}`; the rules read `__meta_docker_container_name` (Docker API names carry a leading slash, e.g. `/obs-ai-service`) to set `service_name` (regex `^/?obs-(.+)$` drops the `obs-` prefix → `ai-service`) plus `container_name`/`container_id`. The Grafana dashboard log panel queries `{service_name="ai-service"}` so this must keep working. **K8s port**: swap `discovery.docker`/`loki.source.docker` for `discovery.kubernetes`/`loki.source.kubernetes` in the same pipeline and re-point the relabel rules at `__meta_kubernetes_pod_*` labels → `kubectl logs` content == Loki. **Do not ALSO ship OTLP logs from an app** (e.g., LoggingHandler) or Loki gets duplicates — `ai-service/tracing.py` no longer attaches a LoggingHandler.
- **ai-service log formatting**: `tracing.py` has no SDK/OTLP code — it only replaces the stdout formatter of root/uvicorn/uvicorn.error/uvicorn.access at **lifespan startup** (called from `main.py`; must run after uvicorn has configured logging: `Config.load()` → `Server._serve` → `lifespan.startup`). It strips ANSI colors and appends `| traceID=… | spanID=…` from the active span, so docker logs text == Loki text and log↔trace correlation survives the switch to stdout collection.
- **ai-service env knobs**: `OTEL_EXPORTER_OTLP_ENDPOINT` (Alloy `http://alloy:4317`), `OTEL_EXPORTER_OTLP_PROTOCOL=grpc`, `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, `TRACELOOP_TRACE_CONTENT` (read directly by OpenLLMetry — content capture, default true). The CLI/distro also honors `OTEL_TRACES/METRICS/LOGS_EXPORTER` (distro setdefaults them to `otlp`). Note `OTEL_LOGS_EXPORTER` is irrelevant in this repo since no app sends OTLP logs anymore.
- **Grafana dashboard JSON hardcodes metric names and datasource uids** (`prometheus`, `loki`, `tempo`) in `config/grafana/dashboards/langchain-observability.json`. Renaming the spanmetrics namespace/metric or a datasource uid silently breaks panels. Datasources auto-provision; dashboards hot-reload ~30s but a *new* dashboard file needs `docker compose restart grafana`.
- **Trace scatter is the built-in `xychart` panel, not the `traces` panel** (panel id 6, verified 2026-09 on Grafana 13.2.2/Tempo plugin 13.2.1). Panel `type` must be `"xychart"` (the plugin id from `panel/xychart/plugin.json`) — `"xy"` renders **"plugin xy not found"**. The `traces` panel (`TracesPanel.tsx`) only renders `transformDataFrames(data.series[0])` — TraceView needs span frames, so a plain TraceQL *search* table frame makes it render **"No data found in response"**. Trace list/scatter must use the `xychart` panel with `mapping: "manual"` + series `frame: byIndex 0`, `x: byName startTime`, `y: byName traceDuration`. Click links come from the **y-field** links (`getFieldDisplayLinks(xySeries.y.field, dataIdx)` in `XYChartPanel.tsx`), so the trace drilldown link lives on `traceDuration` as `{query: "${__data.fields.traceID}", queryType: "traceql"}` — the same shape the backend's own `traceID` column link uses. Clicking it opens TraceView (waterfall bar graph + Flow service graph). The frame's `nested` column (json.RawMessage, spans sub-frames) must be hidden from tooltip via a `byName nested` override or the hover tooltip shows a giant JSON blob.
- **Grafana→Tempo queries verified working end-to-end** (2026-09): panel query `{ resource.service.name = "ai-service" }` (TraceQL, `tableType: traces`) → backend `/api/ds/query` → 200 + "Traces" frame (traceID/startTime/traceService/traceName/traceDuration/nested). Trace drilldown = frontend's `isTraceIdQuery()` (all-hex) auto-converts a `traceql` query to `queryType: traceId` → `/api/traces/{id}` → "Trace" span frame (103 spans for a chat). A bare hex ID sent straight as `queryType: traceql` backendside fails with `parse error: unexpected IDENTIFIER` — the hex→traceId conversion is frontend-only.
- **Grafana creds**: admin/admin; anonymous viewer enabled. UI at http://localhost:3000. Alloy UI at :12345.

## App / LangChain SDK notes (verified 2026-09: langchain 1.4.2, langgraph 1.2.11, OTel SDK 1.44)

- **`create_agent` moved to `langchain.agents`** (`from langchain.agents import create_agent`). `langgraph.prebuilt.create_react_agent` still exists but is deprecated (removal in V2.0). The new signature requires **`tools` positionally — pass `tools=[]`** for no-tools agents. `system_prompt` is still the kwarg name.
- **LangChain has no built-in OpenTelemetry tracer.** Native tracing = `opentelemetry-instrumentation-langchain` (Traceloop OpenLLMetry 0.62.x): `LangchainInstrumentor().instrument()`. Here it's activated by the `opentelemetry-instrument uvicorn main:app ...` CLI (entry point auto-load, Dockerfile CMD), so import order in `main.py` no longer matters — the CLI instruments before the target program runs.
- **FastAPI layer is instrumented by the CLI too**: `FastAPIInstrumentor`'s entry-point `_instrument()` swaps the `fastapi.FastAPI` class for an instrumented subclass, so any app created after instrumentation is auto-wrapped — each `POST /chat/stream` request becomes the trace root span, LangChain spans nested inside. Don't also call `instrument_app(app)` in code (double instrumentation). The only env the LangChain instrumentor reads is `TRACELOOP_TRACE_CONTENT` (verified by grepping 0.62.3 source).
- **SQLite checkpoint/store are packaged inside `langgraph`** (no `langgraph-store` PyPI package; `langgraph-checkpoint-sqlite` is separate). Use async context managers: `AsyncSqliteSaver.from_conn_string("/data/checkpoints.sqlite")` and `AsyncSqliteStore.from_conn_string(...)` — not constructors. **Pass a plain filesystem path, NOT `sqlite:///...`**: aiosqlite hands the string straight to `sqlite3.connect()` (no `uri=True`), so `sqlite:///...` fails with "unable to open database file".
- **ai-service must run with a single uvicorn worker** (one shared SQLite connection; in-memory saver/store state). `--workers 1` is in its Dockerfile.
- **Streaming**: `agent.astream(inputs, config, stream_mode=["messages","updates"])` yields `("messages", (AIMessageChunk, meta))` and `("updates", {node: {"messages": [...]}})`. Chunk text comes from the model node. No OpenAI-specific SPOT dependency — just `streaming=True` on ChatOpenAI.
- **ChatOpenAI base_url must include `/v1`** (`http://mock-llm:8100/v1`). It's a plain OpenAI-compatible HTTP client → also works against real OpenAI/vLLM unchanged.
- **frontend relays SSE** (`POST /api/chat` → ai-service `/chat/stream` → browser). The browser never calls ai-service directly, so CORS isn't actually exercised (ai-service allows `*` anyway). SSE event names: `meta`, `messages`, `updates`, `error`, `done`.
- **OTel logs**: no longer used for the app. Python logging → stdout only; trace/span context is injected by the `_TraceContextFormatter` in `ai-service/tracing.py` (`opentelemetry.trace.get_current_span()` — no `opentelemetry.sdk._logs.LoggingHandler`). If you ever need SDK log export again, `LoggingHandler` lives at `opentelemetry.sdk._logs` (SDK 1.44).
- **mock-llm** is OpenAI-spec compliant for `POST /v1/chat/completions` (stream + non-stream, `data: [DONE]`), plus `/v1/models`, `/health`. `MOCK_LLM_STREAM_DELAY` controls per-token pacing.

## Data flow (why things are where they are)

- Browser → frontend :8080 (`POST /api/chat`, SSE relay) → ai-service :8000 (`/chat/stream`) → ChatOpenAI → mock-llm :8100 (`/v1/chat/completions`). Real model = same path; store multiple model configs in frontend (`models` table) and pick the active one (`settings.active_model`).
- ai-service → Alloy OTLP gRPC :4317 (**traces** via auto-instrumentation). **Logs**: every app prints to stdout and Alloy's `loki.source.docker` collects container stdout → Loki (== `docker logs` content); metrics are derived by Alloy's spanmetrics connector, not emitted by the app.
- Ports: Grafana 3000, Prometheus 9090, Loki 3100, Tempo 3200, Alloy 4317/4318/12345, ai-service 8000, frontend 8080, mock-llm 8100.
- SQLite: ai-service checkpoints/store in volume `ai-service-data` (`/data/checkpoints.sqlite`, `/data/store.sqlite`); frontend models/settings/sessions/messages in `frontend-data` (`/data/frontend.db`).
- Visit `metrics`/`traces` Makefile targets before debugging "no data" — they confirm ingestion end to end.
- Images are pinned; Tempo 3.x and Alloy 1.19 both had breaking config changes. Before bumping versions, re-verify against the official docker-compose examples.
